# vastgrid を必要な人に届ける

2026-11-16 に始める、最初の 30 日の実験計画です。スターは関心を持った人が後で見つけるための結果として増やします。
中心に置く説明は「巨大な CSV・Parquet を、表計算ソフトのように。データは手元で扱える」です。

## いま優先すること

公開時点のスターは 3 件。README・実際に触れるデモ・日英ドキュメント・MIT ライセンス・パッケージの公開は
すでにそろっています。GitHub の topics も CSV・Parquet・DuckDB・React など 20 件が設定済みです。
機能を増やすより、必要としている人に試してもらう機会を作ることを優先します。

訪問数・クローン数・参照元は公開リポジトリに書かず、後述の計測コマンドで `.data/growth/` に保存します。
クローンには自動処理も含まれうるため、人数や利用者数として扱いません。

## 届ける相手と、その人が試す入口

| 優先 | 相手の困りごと | 見せるもの | 次の行動 |
| --- | --- | --- | --- |
| 1 | CSV・Parquet の中身をすぐ確かめたい | [100 万行のサンプル](https://vastgrid.yhay81.com/open/?sample=1) | 自分のファイルを開く → GitHub |
| 2 | 大きいデータを VS Code から出ずに見たい | 拡張機能の画面と導入方法 | 拡張機能を入れる → GitHub |
| 3 | React のアプリに大きな表を組み込みたい | 動く例と正確な性能計測 | quick start → 試作 → GitHub |

最初の投稿では MCP・Jupyter・React などを全部並べません。相手の困りごとを 1 つ選び、
「実物を試す → 自分の作業に使う → 覚えておくためにスター」の順にします。

## 30 日の進め方

日付は日本時間。外部投稿の日付は実施候補で、予約・投稿済みという意味ではありません。

| 期間 | 行動 | 確認する結果 |
| --- | --- | --- |
| 11/16 | README、100 万行への入口、日英の使い方、スター導線を改善。計測の初期値を保存 | リンクとサンプルが動く |
| 11/16–18 | 既存の r/DuckDB 投稿の質問・要望に回答。実データの困りごとを聞く | 会話の内容、再現例、訪問の変化 |
| 11/19–22 | 日本語の短い実演を X に 1 回。CSV/Parquet の読み方を技術記事にまとめる | 投稿後 24/72 時間の訪問とスター増分 |
| 11/23–29 | 前週に反応した用途に合わせた実例を 1 本追加。VS Code か React の片方に絞る | 利用報告、具体的な質問、導入時の詰まり |
| 11/30–12/6 | 試用で見つかった問題を直し、改善内容を同じ会話に返す | 再訪と利用継続の声 |
| 12/7–15 | 効果があった媒体で別の実例を共有。効果がない媒体は休止 | 30 日の純増と次の主力用途 |

既存の [r/DuckDB 投稿](https://www.reddit.com/r/DuckDB/comments/1xwvka1/built_vastgrid_mit_open_100mrow_parquet_csv/)
には、複数の表を視覚的につなぐことと、バージョン管理に関する要望がありました。
同じ告知を再投稿せず、用途を聞いて必要な機能を整理します。まだない機能の提供時期は約束しません。

Product Hunt は、実際の利用例とよくある質問が集まってから判断します。既存の準備作業がある場合は重複させません。
関連する awesome リストへの掲載依頼は、対象リストの条件を確認し、利用例ができてから個別に行います。

Hacker News は、現在の [ガイドライン](https://news.ycombinator.com/newsguidelines.html)が生成・AI 編集した文章と
自動投稿を認めていません。候補にする場合は、作者自身が体験を書き、手動で投稿します。
[Show HN の条件](https://news.ycombinator.com/showhn.html)を確認し、デモ・計測条件・制限を手元の材料にします。

## 仮の目標と、続けるかの判断

**14 日で 25 スター、30 日で 100 スター**を仮の到達目標にします。予測や保証ではありません。
3 → 100 には 97 件の純増が必要です。仮に新規訪問からのスター率が 5% なら約 1,940 人の訪問が必要ですが、
5% は未検証の仮定です。まず訪問と実際の利用反応が増えるかを確かめます。

- 2 回の内容を変えた発信でも訪問がほとんど増えなければ、媒体か相手を変える。
- 訪問が増えても利用反応がなければ、最初の操作と用途の説明を見直す。
- 反応・質問がある用途には、実例と改善を追加する。
- 公開投稿の閲覧数、GitHub の訪問者、スター増分は別々に記録する。同じ人と特定できないので、
  スターを特定の投稿の成果と断定しない。

## 計測

GitHub CLI の `gh auth login` を済ませ、リポジトリに push 権限のあるアカウントで実行します。

```sh
pnpm growth:snapshot
```

取得するのはスター・fork・説明・topics と、直近 14 日の訪問・クローン・参照元・人気ページです。
認証情報や訪問者個人の情報は保存しません。結果は Git 管理外の `.data/growth/yhay81--vastgrid/` に保存します。
トラフィックを取得できない場合は `available: false` とし、ゼロに置き換えません。

発信前、24 時間後、72 時間後、7 日後に実行してスターの差分を確認します。
[GitHub のトラフィック](https://docs.github.com/en/repositories/viewing-activity-and-data-for-your-repository/viewing-traffic-to-a-repository)
は直近 14 日の集計です。毎回の数値を足してはいけません。日別の訪問数は日付で照合し、
異なる日のユニーク訪問者数を足しても期間全体のユニーク人数にはなりません。
スター総数 ÷ 14 日の訪問者数も、獲得率ではありません。

投稿には媒体ごとに `utm_source` を付けたサイトのリンクを使えます。ただし UTM はリンクの目印です。
現在の実装はクリック計測やサイト分析を追加しておらず、GitHub はその値をスターに結び付けません。
投稿 URL・投稿時刻・内容・24/72 時間後の差分を記録して比較します。

| 投稿 URL | 公開日時（JST） | 相手・用途 | 発信前のスター | 24 時間後 | 72 時間後 | 得られた質問 |
| --- | --- | --- | ---: | ---: | ---: | --- |
| 実際に公開してから記入 | | | | | | |

大量の同文投稿、スター購入、相互スター、無関係な issue への宣伝は行いません。
